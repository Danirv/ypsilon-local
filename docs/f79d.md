# Runxin F79D profile

The F79D profile is the device knowledge currently used by Ypsilon. Field ids, read codecs and known legacy write encodings live in `runxin/fields.py`; `runxin/f79d.py` turns that catalogue into frames and decoded state.

## Evidence legend

- **A** — present in the legacy WaterDevice field/codec implementation;
- **O** — value/behavior observed on the project's real Ypsilon/F79D data;
- **HW** — local write exercised end-to-end against the physical controller and confirmed through an independent fresh local read-back;
- **CW** — value change observed through the legacy cloud application.

`A` proves application support, not that every Runxin firmware or rebrand behaves identically.

## Endianness correction in 2.6.0

The legacy WaterDevice codec serialises field 7 with its generic little-endian helper. Field 11 is different: WaterDevice explicitly reverses that two-byte array before decoding, therefore its wire representation is big-endian.

Earlier Ypsilon versions used BE for field 7 in both write and read paths. That implementation could self-confirm a write because the same incorrect interpretation was used in both directions. Version 2.6.0 follows the legacy codec and withdraws the previous `HW` evidence for field 7 until the corrected LE implementation is physically revalidated.

## Unit-dependent volume-pair reconstruction

Fields 35, 37, 39 and 41 consume the immediately following continuation field. Let the relevant bytes be:

```text
base field:          [id, base_low, base_high]
continuation field:  [id+1, next_low, next_high]
```

The legacy application constructs the logical three-byte value as:

```text
[next_high, next_low, base_high]
```

and then interprets it according to `waterVolumeUnit`:

- unit `0` or `1`: 24-bit little-endian integer
  `next_high + (next_low << 8) + (base_high << 16)`;
- unit `2`: decimal/base-100 packing
  `next_high + next_low*100 + base_high*10000`, presented by Ypsilon in cubic metres with `/100` scaling.

If the unit field or continuation field is missing, Ypsilon returns `None` rather than fabricating a plausible zero.

## Flow units

The legacy UI labels field 11 as:

- unit 0: `gpm`;
- unit 1: `Lpm` (`L/min`);
- unit 2: `m³/h`.

Only unit 2 has been calibrated end-to-end on the project's physical Ypsilon G6. The field-7 Home Assistant control therefore remains available only in unit code 2.

## Vacation semantics

Field 49 is the vacation flag. The legacy UI only enters vacation from `systemMode == 0` and exits from the stable vacation position `systemMode == 8`.

Ypsilon keeps the raw `station` value and adds a separate semantic state:

- `off`: field 49 is false;
- `preparing`: field 49 is true but station is not 8;
- `active`: field 49 is true and station is 8.

Stable `vacation + station 8` is not considered mechanical activity for adaptive polling. Transition phases remain active-poll states.

## System-close reasons

Known legacy UI reason codes for field 12:

| Raw | Stable semantic key |

| 257 | `manual_close` |
| 513 | `leak_detected` |
| 769 | `continuous_flow_timeout` |
| 1025 | `flow_rate_exceeded` |

The raw numeric code is always retained.

## Safe Home Assistant write surface

The protocol codec knows how to serialise more fields than Home Assistant exposes. The generic administrator `write_fields` service is deliberately limited to reversible configuration fields and applies range/unit validation. Field 34 and field 49 are excluded from that generic service so their state-machine semantics cannot be bypassed.

## Hardware write verification status

Currently verified locally end-to-end:

- field 4 — device clock;
- field 6 — continuous-flow limit;
- field 10 — regeneration trigger time;
- field 43 — salt addition;
- field 47 — raw-water hardness.

Pending/revalidation required:

- field 7 — flow cutoff, after the 2.6 LE correction;
- field 34 — forced regeneration;
- field 49 — vacation mode.

## Field 52 polling

The normal state query remains fields 1..51. Field 52 is read separately and cached by the Ypsilon integration. That is an integration polling policy, not part of the generic Runxin transport contract.
