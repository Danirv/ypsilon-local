# Runxin F79D profile

The F79D profile is the device knowledge currently used by Ypsilon. Field ids,
read codecs and known legacy write encodings are defined in
`runxin/fields.py`; `runxin/f79d.py` turns that catalogue into frames and decoded
state.

## Evidence legend

- **A** — present in the legacy WaterDevice field/codec implementation;
- **O** — value/behavior observed on the project's real Ypsilon/F79D data;
- **HW** — local write exercised end-to-end against the physical controller and confirmed through an independent local read-back;
- **CW** — a value change was observed through the legacy cloud application.

`A` is evidence of application support, not proof that every F79D firmware or rebranded device implements the field identically.

## Work-pattern semantics

The legacy WaterDevice application contains an explicit enum for field 9. Ypsilon exposes the same mapping as a read-only Home Assistant enum:

| Raw | Stable state | Legacy app label |
|---:|---|---|
| 0 | `downflow_meter_delayed` | DF Meter delayed |
| 1 | `downflow_meter_immediate` | DF Meter immediate |
| 2 | `downflow_intelligent_meter_delayed` | DF Intelligent meter delayed |
| 3 | `upflow_meter_delayed` | UF Meter delayed |
| 4 | `upflow_meter_immediate` | UF Meter immediate |
| 5 | `upflow_intelligent_meter_delayed` | UF Intelligent meter delayed |
| 6 | `filter_type` | Filter type |
| 7 | `meter_delayed` | Meter delayed |
| 8 | `meter_immediate` | Meter immediate |
| 9 | `intelligent_meter_delayed` | Intelligent meter delayed |

Codes 0..6 are also consistent with Runxin's published down-flow, up-flow and filter mode families. The integration intentionally does not expose field 9 as a write control: knowing a legacy encoding is not enough to declare a mechanical configuration safe.

## Hardware write verification status

The following Home Assistant controls have been exercised against the project's physical ATH/BWT Ypsilon G6 / Runxin F79D and confirmed through the integration's strict local read-back path:

- field 4 — device clock / clock sync;
- field 6 — continuous-flow limit;
- field 7 — flow shutoff threshold;
- field 10 — regeneration trigger time;
- field 43 — salt addition;
- field 47 — raw-water hardness.

Two exposed actions remain intentionally unmarked as hardware-write verified:

- field 34 — forced regeneration;
- field 49 — vacation mode.

Do not promote either to `HW` evidence until the physical controller has been observed to enter/leave the corresponding state and an independent local read confirms it.

## Volume-pair reconstruction

Fields 35, 37, 39 and 41 require the immediately following continuation field. The formula recovered from the legacy codec and retained for compatibility is:

```text
value = (continuation_high
         + continuation_low * 100
         + base_high * 10000) / 100
```

The base field's low byte is not part of that formula. For the project's verified `waterVolumeUnit = 2`, the resulting volume values are cubic metres. Field 11 is a separate instantaneous service-flow value in hundredths; with unit code 2 it is exposed as cubic metres per hour.

## Regeneration semantics

`regenerationPattern` is the high-level regeneration criterion:

- `0`: metered / volume-based;
- `1`: time / day-based.

`workPattern` is the more specific controller strategy described above. The two fields are therefore complementary rather than aliases.

For the project's device, metered/volume mode is the normal configuration. `residualWaterProduction` is remaining treatment capacity, not water physically stored in a tank. `operationDay` and `remainingDay` are mainly relevant in the time/day path.

The legacy cloud payload also contains `regenerationTimes`, but no local F79D field mapping has been proven. Ypsilon does not invent one and does not expose a derived local entity for it.

## Home Assistant statistics semantics

State classes are assigned according to the current Home Assistant sensor model:

- `flowRate` — `measurement`: a present-time flow reading;
- `dailyWaterConsumption` — `total_increasing`: a cumulative daily total that can reset for a new meter cycle;
- `residualWaterProduction` — `measurement`: a present remaining-capacity state;
- `averageWeeklyWaterConsumption` — no state class because it is already a historical aggregation;
- `periodicWaterProduction` — no state class because it is a controller-provided periodic/configured quantity, not a present measurement or a cumulative meter.

This avoids asking Home Assistant to build misleading long-term statistics from already-aggregated or configuration-like values.

## Safe Home Assistant write surface

The codec knows encodings for more fields than the integration exposes. The administrator-only raw service is deliberately narrower than the codec's known write encodings. A field must not be added merely because the old application contains an encoder; a syntactically valid mechanical setting can still be unsafe.

Normal entities expose a smaller, purpose-specific set with ranges and strict physical read-back. Evidence in this document records what has actually been verified on hardware and is intentionally independent from mere codec support.

## Field 52 polling

The normal state query is fields 1..51. Field 52 is read separately and cached for one hour by the Ypsilon adapter. That is an integration/device polling optimization, not part of the generic Runxin transport contract.
