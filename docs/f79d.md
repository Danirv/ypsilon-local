# Runxin F79D profile

The F79D profile is the device knowledge currently used by Ypsilon. Field ids, read codecs and known write encodings live in `runxin/fields.py`; `runxin/f79d.py` turns that catalogue into frames and decoded state.

For the evidence trail behind the legacy WaterDevice application, real-device observations and safety decisions, also see [`waterdevice-audit.md`](waterdevice-audit.md). Recovered advanced-setting enum maps, numeric ranges and their Home Assistant surface are documented in [`f79d-settings.md`](f79d-settings.md) ([ES](f79d-settings.es.md), [CA](f79d-settings.ca.md)).

## Evidence legend

- **A** — present in the legacy WaterDevice field/codec implementation;
- **O** — value/behavior observed on the project's real Ypsilon/F79D data;
- **HW** — local write exercised end-to-end against the physical controller and confirmed through an independent fresh local read-back;
- **CW** — value change observed through the vendor/cloud application path.

`A` documents recovered application behavior. It does **not** override contradictory physical-controller evidence. A transport ACK without matching fresh read-back is not `HW` evidence.

## Field 7 hardware endianness correction in 2.6.3

Physical G6 evidence is decisive:

```text
wire bytes: 03 E8
BE: 0x03E8 = 1000 -> 10.00 m³/h
LE: 0xE803 = 59395 -> 593.95 m³/h
```

The vendor application showed 10.00 m³/h while Ypsilon 2.6.2, using the LE regression, showed 593.95 m³/h. This proves that this controller's field 7 wire representation is big-endian.

The write path independently confirms the same conclusion. A requested 2.00 m³/h is raw 200 (`0x00C8`) and must be sent as `00 C8`. The LE regression sent `C8 00`; the transport ACKed the frame but repeated fresh reads kept the previous physical value, so Ypsilon correctly raised `Write ACKed but not confirmed`. Earlier project versions using BE had already completed successful physical write/read-back validation. Field 7 is therefore restored to `HARDWARE_WRITE_VERIFIED`.

The recovered legacy WaterDevice code appeared to use a generic little-endian helper for field 7. For interoperability documentation that discrepancy is retained rather than hidden, but observed controller bytes and independent physical read-back take precedence for the tested Ypsilon G6.

## Home Assistant surface for recovered advanced settings

Fields 2, 3, 24 and 48 are genuine WaterDevice enums and are exposed as Home Assistant enum sensors rather than raw integer sensors. They are diagnostics disabled by default, preserve stable untranslated state keys, and retain the controller code in `raw_code`.

Fields 13, 14 and 25 are numeric settings, not enums. Fields 13 and 14 remain disabled-by-default read-only diagnostics. Field 25 is enabled by default because it is the controller's native regeneration-count threshold for the resin-maintenance reminder; it is not a current or lifetime regeneration counter.

## Unit-dependent volume-pair reconstruction

Fields 35, 37, 39 and 41 consume the immediately following continuation field. Let the relevant bytes be:

```text
base field:          [id, base_low, base_high]
continuation field:  [id+1, next_low, next_high]
```

The legacy application constructs the logical three-byte value as `[next_high, next_low, base_high]` and interprets it according to `waterVolumeUnit`:

- unit `0` or `1`: 24-bit little-endian integer `next_high + (next_low << 8) + (base_high << 16)`;
- unit `2`: decimal/base-100 packing `next_high + next_low*100 + base_high*10000`, presented in cubic metres with `/100` scaling.

If the unit field or continuation field is missing, Ypsilon returns `None` rather than fabricating a plausible zero.

## Water/statistics semantics

- Fields 37–38 are the within-day cumulative consumption counter and reset around the day boundary. Home Assistant uses `TOTAL_INCREASING`.
- Fields 39–40 are the controller-reported weekly average, not the vendor app's historical weekly bars, and intentionally have no `state_class`.
- Fields 41–42 are treatment capacity per cycle, not a cumulative consumption meter, and intentionally have no `state_class`.
- Fields 35–36 are remaining treatment capacity and are exposed as a measurement.

Older releases briefly generated long-term statistics for fields 39 and 41. Home Assistant may offer to remove those obsolete statistics after upgrade; that cleanup does not remove the entities or their normal recorder history.

## Flow units and field-7 limits

The legacy UI labels field 11 as unit 0 `gpm`, unit 1 `Lpm` (`L/min`) and unit 2 `m³/h`. Only unit 2 has been calibrated end-to-end on the project's physical Ypsilon G6. The field-7 Home Assistant control therefore remains available only in unit code 2 and is constrained to 0–10.00 m³/h, matching raw hundredths 0–1000. Field 6 remains constrained to 0–120 minutes.

## Salt semantics

Field 43 is the legacy `addSalt` setting: a 0–100 kg **amount of salt added**. Local SET/read-back has been physically verified and the same value has also been observed changing through the vendor path. It is not a physical remaining-salt sensor; low-brine and add-salt/reminder conditions are separate controller fields 31 and 33.

## Vacation semantics and safety decision

The recovered legacy UI models vacation mode using field 49 and the sequence `0 -> 3 -> 7 -> 2 -> 8`, but on the project's physical G6 a direct local field-49 write was ACKed without changing fresh read-back state. Consequently Ypsilon continues reading field 49 and preserves codec support for research, but does not mark it `HARDWARE_WRITE_VERIFIED` or expose a writable Vacation switch. Derived state remains `off`, `preparing` and `active` (`vacationPattern=true` + `station=8`).

## Safe Home Assistant write surface

The protocol codec knows how to serialise more fields than Home Assistant exposes. The generic administrator `write_fields` service is deliberately limited to reversible configuration fields and applies range/unit validation. Fields 34 and 49 are excluded from that generic service. Field 49 has no purpose-specific HA writer because its local current-firmware action is not physically verified.

## Hardware write verification status

Verified locally end-to-end on the project G6:

- field 4 — device clock;
- field 6 — continuous-flow limit;
- field 7 — flow-rate cutoff, **u16 BE**;
- field 10 — regeneration trigger time;
- field 43 — salt addition;
- field 47 — raw-water hardness.

Pending/unverified:

- field 34 — mechanical regeneration/state-machine controls beyond specifically tested behavior;
- field 49 — direct local write disproved on the tested G6; no HA control until a correct local sequence is physically verified.

## Field 52 polling

The normal state query remains fields 1..51. Field 52 is read separately and cached by the Ypsilon integration because it is a slow-changing service interval. That is an integration polling policy, not part of the generic Runxin transport contract.
