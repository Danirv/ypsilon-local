# Runxin F79D profile

The F79D profile is the device knowledge currently used by Ypsilon. Field ids,
read codecs and known legacy write encodings are defined in
`runxin/fields.py`; `runxin/f79d.py` turns that catalogue into frames and decoded
state.

## Evidence legend

- **A** — present in the legacy WaterDevice field/codec implementation;
- **O** — value/behavior observed on the project's real Ypsilon/F79D data;
- **HW** — local write exercised end-to-end against the physical controller and
  confirmed through an independent local read-back;
- **CW** — a value change was observed through the legacy cloud application.

`A` is evidence of application support, not proof that every F79D firmware or
rebranded device implements the field identically.

## Hardware write verification status

The following Home Assistant controls have been exercised against the project's
physical ATH/BWT Ypsilon G6 / Runxin F79D and confirmed through the
integration's strict local read-back path:

- field 4 — device clock / clock sync;
- field 6 — continuous-flow limit;
- field 7 — flow shutoff threshold;
- field 10 — regeneration trigger time;
- field 43 — salt addition;
- field 47 — raw-water hardness.

Two exposed actions remain intentionally unmarked as hardware-write verified:

- field 34 — forced regeneration;
- field 49 — vacation mode.

Do not promote either to `HW` evidence until the physical controller has been
observed to enter/leave the corresponding state and an independent local read
confirms it.

## Volume-pair reconstruction

Fields 35, 37, 39 and 41 require the immediately following continuation field.
The formula recovered from the legacy codec and retained for compatibility is:

```text
value = (continuation_high
         + continuation_low * 100
         + base_high * 10000) / 100
```

The base field's low byte is not part of that formula. Offline regression tests
pin the current behavior so a refactor cannot silently change historical values.

## Regeneration semantics

`regenerationPattern` is model-dependent UI state in the legacy application:

- `0`: flow/volume based;
- `1`: time/day based.

For the project's device, flow/volume mode is the normal configuration.
`residualWaterProduction` is therefore remaining treatment capacity, not water
physically stored in a tank. `operationDay` / `remainingDay` are mainly relevant
in time/day mode.

## Safe Home Assistant write surface

The codec knows encodings for more fields than the integration exposes. The
administrator-only raw service is deliberately narrower than the codec's known
write encodings. A field must not be added merely because the old application
contains an encoder; a syntactically valid mechanical setting can still be
unsafe.

Normal entities expose a smaller, purpose-specific set with ranges and strict
physical read-back. Evidence in this document records what has actually been
verified on hardware and is intentionally independent from mere codec support.

## Field 52 polling

The normal state query is fields 1..51. Field 52 is read separately and cached
for one hour by the Ypsilon adapter. That is an integration/device polling
optimization, not part of the generic Runxin transport contract.
